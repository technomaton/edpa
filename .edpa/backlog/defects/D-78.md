## Symptom

`project_setup.py --check-hooks` in EDPA's own repo reports all four hooks as
`NOT EDPA-managed`, `purpose not wired` — while they demonstrably work
(`chore(evidence):` commits are being produced).

## Cause

`_is_edpa_owned()` classifies purely on the `EDPA-MANAGED-HOOK` sentinel.
Hooks installed before the sentinel was introduced carry the same executable
body but an older comment header, so they are classified `foreign`.

Consequences:
1. `--refresh-hooks` (the update_engine.sh self-heal path) never overwrites
   them → hook fixes from `/plugin update` never propagate into the repo.
2. The doctor cries wolf 4x on a correctly-wired repo, training users to
   ignore it.

Every repo set up before the sentinel landed is affected, not just this one.

## Verification

`diff .git/hooks/<h> .edpa/engine/scripts/hooks/<src>` for all four hooks is
comments-only — zero functional drift. So re-stamping is lossless.

## Fix

Classify on the executable body, not the header: when the sentinel is absent
but the comment-stripped body matches the vendored source, treat the hook as
EDPA-owned (legacy) so refresh re-stamps it.
