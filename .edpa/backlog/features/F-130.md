Ticket IDs came from a counter inside one working tree, so two worktrees,
clones or developers minted the same number and only found out at merge
time. Measured on the consumer pilot (2026-10-07): 28 worktrees over one
clone, each with its own counter; 167 new tickets in 30 days from 5
people; 111 of 233 commits on main rewriting `id_counters.yaml`; 9 of the
last 60 PRs existing only to "reserve" a ticket ID through an 11-minute
PR.

This feature moves the arbiter to the git remote the team already pushes
to — the ID ledger, a compare-and-swap on a ref — without bringing back
any forge API (decision record 14 in `docs/v2/decisions.md`; going back
to GitHub issue numbers was considered and rejected there).

Stories, in dependency order: ledger protocol, allocator integration,
CLI, write layer, hooks, renumber + PI planning server, docs. The last
story (ledger-aware parents) is an optional extension awaiting a
decision.

Out of scope: releasing a version, and switching any repository over
(`init-remote` writes to a shared remote — a deliberate, per-repository
step).
