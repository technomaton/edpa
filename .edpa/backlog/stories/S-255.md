## Policy change

Supersedes the "EDPA never edits your lefthook config" stance from S-254.

`extends: - .edpa/engine/lefthook-edpa.yml` becomes the **default and preferred**
registration path. EDPA writes that line into the user's lefthook config itself,
and a repo on any other setup (hand-pasted block, partial paste) is migrated to
it on `/plugin update`.

## Hard scope boundary

EDPA edits **exactly one thing** in a user's lefthook config: the `extends:`
entry pointing at the vendored fragment. Never anything else — no removing a
stale hand-pasted block, no reordering, no reformatting, no touching unrelated
hooks or commands. A leftover manual block is harmless: the fragment wins a
name collision and its `run:` lines are byte-identical.

## Why this is safe to leave alone

Verified empirically on lefthook 1.7.22 and 2.1.10: merged config is identical
whether or not the old manual block is present.

## Where it must fire

- `install_hooks` lefthook branch (`--with-hooks` / `--refresh-hooks`)
- `update_engine.sh` after vendoring — the migration path

## Constraints

- Idempotent: a config already referencing the fragment is left untouched.
- YAML configs only (`.yml`/`.yaml`). `lefthook.toml` / `.json` cannot be
  safely line-edited — fall back to printing instructions.
- Preserve comments and formatting; no YAML round-trip.
- Announce the edit loudly — it is a write to a user-owned file.
